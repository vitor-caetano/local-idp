The golden path, end to end

What happens between clicking Create in Backstage and a Go service answering at https://<name>.localtest.me. Every hand-off goes through Git, and every step below was observed on this cluster with hello-go.

The whole loop

Two loops meet at one Git repository. Events push a build forward; ArgoCD pulls the result back out.

The one rule: Git is the only hand-off. To know what is running, read manifests/kustomization.yaml in the service repo. To change it, commit.

1Scaffold in Backstage

The go-service template runs three actions. Each one leaves something behind.

What the repo holds

A standard-library Go server (/, /healthz, /metrics), its Dockerfile, and manifests/: Rollout, Service, HTTPRoute, ServiceMonitor, ScaledObject, tied together by a kustomization.

The first sync pulls a missing image

The kustomization starts at newTag: "initial", which does not exist. The Rollout shows ImagePullBackOff until the first build commits a real tag, usually within a minute.

2From push to build request

Gitea calls a webhook on every push in the services org. The Sensor decides which pushes deserve a build.

What the Sensor passes on

body.repository.clone_url, body.repository.name and body.after (the commit SHA) become the Workflow parameters.

Why Gitea is allowed to call in

Gitea blocks webhooks to private addresses unless webhook.ALLOWED_HOST_LIST: private is set, which it is.

3The CI Workflow

ci-go-service runs four steps in the ci namespace as ci-runner. It has two outputs: an image and a commit.

Why ci is privileged

Rootless BuildKit needs seccomp and AppArmor unconfined, so ci is a privileged Pod Security namespace. Nothing but build pods runs there.

Cleanup

Step pods are deleted when a Workflow succeeds; failed ones stay for debugging. The Workflow object itself is deleted an hour after it finishes.

4GitOps: ArgoCD takes over

Nobody creates an ArgoCD Application by hand. An ApplicationSet discovers service repos and generates one per repo.

Sync policy

Automated with prune and selfHeal, and server-side apply. A manual kubectl edit in apps is reverted.

Timing

New repos appear within about a minute. A new commit is picked up on ArgoCD's repo poll, about three minutes, which is most of the delay between a build finishing and the rollout starting.

Synced means Git matches

The manifests spell out fields the API server would default (route group, kind, weight, port protocol), or ArgoCD would report OutOfSync forever.

5The canary rollout

The workload is an Argo Rollout, not a Deployment. A new tag goes out in two steps: half, then all.

Who owns replicas

The Rollout has no replicas field. KEDA sets it (see below), so ArgoCD and the autoscaler never fight over it.

Rolling back

Revert the tag commit in the service repo. ArgoCD syncs the old tag and the Rollout runs the same two steps back to it.

6The running service

Two paths matter once it is up: how a request reaches a pod, and how the pod count follows load.

Guardrails

Kyverno enforces three rules in namespaces labelled local-idp.dev/policy=enforce, which today is only apps. The golden path satisfies all three by construction.

PolicyRuleHow the golden path meets it
golden-path-restrict-registriesImages come from localhost:5001/CI pushes there; the kustomization points there.
golden-path-disallow-latestAn explicit tag, never latestThe tag is the commit SHA.
golden-path-require-non-rootrunAsNonRoot: trueThe skeleton runs as uid 65532.

Try it: ./scripts/denial-demo.sh applies a docker.io/library/nginx:latest Pod to apps and shows all three denials, then shows the same Pod admitted in default.

When it breaks, look here

Follow the flow in order. The first place the trail goes cold is the problem.

SymptomFirst place to look
Template fails in BackstageThe task log on the Create page; then kubectl -n backstage logs deploy/backstage
